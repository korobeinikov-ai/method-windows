# {{ИМЯ}} — правила проекта

Проект ведётся по методу KOROBEINIKOV AI. Владелец проекта — архитектор: отвечает за логику, процессы
и решения. Claude отвечает за технику и делает её сам. Полные правила метода подмешивает пакет;
главные продублированы здесь — они действуют, даже если пакет не загрузился.
Пакет загрузился — в начале разговора есть «Правила KOROBEINIKOV AI». Их нет — первым делом скажи
владельцу одной строкой, что пакет не загрузился (охраны и опыта метода сейчас нет), и помоги включить (`/plugin`).

## Главные правила
- Говорить по-русски, просто, сравнениями на уровне Excel. Сначала «что и зачем», код — по просьбе.
- Всё, что можно сделать самому, — делать самому. Владельцу — только регистрация, оплата, вход,
  «разрешить»; на каждый такой шаг — прямая ссылка и что нажать.
- Секреты (ключи, пароли, токены) — только в `.env`. `.env` никогда не в git, значения не выводить.
  Ключ попал в код или в git → вынести в `.env` и сказать владельцу: ключ надо заменить.
- Готово = доказано: правка закончена, когда проверена делом (запуск, открытый результат). Только
  потом сохранять в git — поимённо, посмотрев изменения на секреты. Проверку секретов при сохранении
  не обходить никогда (`--no-verify`, отключение `.githooks`): нашла секрет — убрать его в `.env`.
- Ошибка не молчит: либо пишется в журнал, либо всплывает наверх.
- Один шаг за раз. Новый сервис подключать, только когда задача требует, и объяснить зачем.
- Перед работой с частью проекта — прочитать её карту `STRUCTURE.md`; изменил устройство — обновить карту.

## Нужно → где
| Нужно | Где |
|---|---|
| Зачем всё дело, решения владельца, что дальше | `IDEYA.md` |
| Из чего состоит проект, как части связаны, куда смотреть | `STRUCTURE.md` |
| Ключи и пароли | `.env` — только на этом компьютере; образец без значений — `.env.example` |
| Проверка секретов перед каждым сохранением | `.githooks/pre-commit` (сканер gitleaks, свои правила — `.gitleaks.toml`) |
| Предпочтения владельца, найденные грабли | память Claude (только то, чего нет в файлах проекта) |

## Порядок
- В начале работы — прочитать `IDEYA.md` и `STRUCTURE.md`: зачем всё дело и из чего оно состоит.
- `IDEYA.md` — основа. Владелец что-то решил — строкой в «Решения владельца» (дата — решение — почему).
  Задача закрыта — обновить «Что дальше». Суть («Зачем и для кого») меняется только с «да» владельца:
  мысль сильно поменялась — спросить «меняем направление — переписать основу?», не дописывать молча.
- Основа — коротко, только суть всего дела; подробности части — в её карте.
- Каждая самостоятельная вещь (отчёты, бот, сайт) — своя папка со своей картой `STRUCTURE.md`.
  Части начали брать данные друг у друга — записать в карте проекта, в «Как части связаны», стрелками.
- Один факт — одно место, в остальных — ссылка. Документ описывает, как есть сейчас.
